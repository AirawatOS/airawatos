§ Solution Studio · v-next design

You don't fill a form.
You tell the court's story.

The next Solution Studio treats a solution as what it actually is — a graph of component-configurations — and lets a domain expert author it by narrating their process and reviewing forms, never a schema. This is that design, walked end-to-end through a real build: Court 1 case management.

ADR-0076 · process-first authoring one graph, three lenses reuse-first

The thesis in three lines

what it is

A set of component-configs

A solution reduces to (component, config-in-scope) tuples plus their wiring. Install fans them out. That's the whole substrate.

how you think

An 8-layer anatomy

Domain · data · insight · rules · decisions · agents · platform services · surfaces. A lens for completeness — internal, never the author's screen.

how you author

A process, told aloud

Narrate who does what to what. The Expert drafts the forms & flow you review; the graph is written underneath, reuse-first.

The domain author's lens · conversational

Six moments, no schema in sight

This is what a court registrar — not a developer — sees. They never touch a JSON schema, a component id, or the word "closure." They talk, review forms, and confirm.

1Entry

What starts this — a person, or data?

The first and only structural question. It picks the shape of everything downstream, because a solution's front is always a data source — and a data source is either a person filling a form or a signal arriving.

new solution
Does a person start this by entering something, or does data (a sensor, a feed) start it?
A person. An advocate files a case.
Two entry types, one spine. Court = user-initiated → the author will review a form. (An air-quality solution would be observation-initiated → they'd review a data source + map.) After the entry point, both converge on the identical rules → workflow → decision spine.
2Seed

Tell me the process — or hand me the document

The registrar has a spreadsheet the court already wrote: entities, roles, states, and an action table (actor → action → object → state change). That table is the process story. They upload it instead of re-keying it.

intake
▸ uploaded Justice.xlsx — 43 entities, 34 verbs, 7 state machines
Read it. The action sheet reads as your process: an advocate files → a scrutiny officer checks → returns for defects, or the registrar registers and a number is assigned → a bench clerk lists a hearing → the judge hears and disposes. Confirm and I'll build against it.
Documents are raw material, not a separate path. Upload or narration both seed the same review. Everything the Expert proposes carries a citation back to a cell, a state, an action — the author is always reviewing a grounded proposal, never a black box.
3Reuse

Almost all of this already exists

Before proposing anything new, the Expert searches the marketplace for every noun in the story. For Court 1 it finds a signed justice pack — ten schemas, three roles, an interface — and reuses them. Only the true gaps are proposed as new.

Reuse is the safeguard. "Reuse justice.case" is high-confidence and safe; "generate a new component" is where extraction goes wrong. So generation is the exception, quarantined behind an explicit gap — and nothing enters the graph without a citation and a confidence score.
4Review

Review the form and the flow — that's it

The author confirms the solution by looking at the two things they understand: the form a person fills, and the flow the case moves through. The schemas, the workflow declaration, the decision spine are generated behind these.

5Handoff

What the author can't do gets routed, not dumped

A domain author can define the process, the forms, the rules, the decisions — everything they own. They structurally cannot govern a new schema (steward authority), write code (a developer), or hold a secret (the operator). v-next doesn't dead-end there; it turns each gap into a routed ticket that lives on the node.

90% reuse changes the endgame. Because the marketplace already held the model, Court 1 needs zero new code and zero operator setup — only a steward approval and a builder wiring pass. The author gets a near-complete solution from their spreadsheet in one sitting.
6Ship

Green rail → install → clickable

As handoffs return, their tickets flip green on the author's canvas. When the last clears, the self-contained-closure check passes — the solution declares a producer for everything it reads — and publish is a non-event. Install fans the graph into the court-1 tenant, and the registrar logs in to a working court.

The architecture

One graph, three lenses

The domain author's conversation, the builder's canvas, and the developer's code editor are not three tools. They are three lenses on one solution graph — the same (component, config) tuples, rendered for who's looking. v-next builds the shared graph first; every door reads and writes it.

Underneath · the internal lens

The anatomy Court 1 fills

The author never saw these eight layers — but the Studio tracked them, and this is how a builder or steward reads the solution's completeness. Justice fills them like this:

  • 1 · domainCase, Hearing, Filing, Court, Party, Evidence, Process, Disposal + 6 roles + verbs
  • 2 · datauser-entered forms (this is a user-initiated solution — no drivers)
  • 3 · insightnone — pure casework, no derived measures (a court-load dashboard could add one later)
  • 4 · rulesscrutiny checklist · limitation period · fee-due — extracted from the guideline
  • 5 · decisionsscrutiny accept/return · bail grant/reject · disposal — the judge decides, never the system
  • 6 · agentsoptional — a cause-list assistant, a next-date suggester
  • 7 · platformworkflow = case lifecycle · notifications = hearing reminders · payment = court fee (deferred)
  • 8 · surfacescontributes into Inbox (tasks), Visualize (cause list), Files (orders) — no new app shell
The anatomy is a lens, not the author's UI. It tells a builder what a complete solution needs and lets the Studio show gaps ("layer 4: no rules yet") — while the domain author only ever sees forms, flows, and maps.

Build order

Five slices, author-first

  1. Shared graph model. One solution declaration (ADR-0045 fields + platform block + contributions + closure) that both doors bind to. The foundation — built before either lens.
  2. Document intake + reuse-first extraction. Ingest → cited process story → marketplace reuse search per noun → proposed graph. This is where the 90% moment lives.
  3. Conversational confirm/edit. The domain author's lens: entry-type, form & flow review, plain-language edits, "why is this here?" citations.
  4. Handoff tickets. Routable per-node objects (steward / builder / component-dev / operator) with live green/red reconvergence — the load-bearing new primitive.
  5. Builder canvas & code panel. The other two lenses onto the same graph, with the live validation rail.

Slices 1–4 give a non-coder a complete experience — and simultaneously build the shared model and ticket rail that the builder and developer lenses plug into. Court 1 is the acceptance test: a registrar turns a spreadsheet into a running court without seeing a schema.
