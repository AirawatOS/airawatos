AirawatOS · Architecture Review · 2026-10-31

Trusted Network Platform — four planes, one spine

The design direction for evolving AirawatOS from a service/credential core into a generic Trusted Network Platform on which networks like Avsar (service & credential exchange) and TOP (event exchange) are configuration, not code.

ADR-0119 / 0120 / plan approved Phase 1 design rev 3 — awaiting sign-off (impl on hold) Design only · no code written

01The question & the verdict

Is this a genuine generic platform on which Avsar and TOP can both be configured — or an Avsar-specific build partially generalized?

As-built today: a genuinely generic platform for the service/credential exchange pattern (Avsar-class). The kernel and network authority carry essentially no domain logic; native and external participants already share one service abstraction.

But not yet a multi-pattern Trusted Network Platform: the event-exchange plane (resources, authority, events, subscriptions, routing) does not exist, so TOP cannot be configured without new code. This design closes that gap while correcting five ontology weaknesses — without a rewrite.

02Four orthogonal planes

One system, presented as four planes. Service-exchange and event-exchange are two runtimes in the Exchange plane standing on the same Trust, Knowledge and Governance — not two engines. That shared spine is what makes the two patterns configurations of one platform.

03The ontology corrections (D1–D11)

Eleven decisions turn the as-built weaknesses into a clean model. All are design; each corrects a specific as-built gap.

#DecisionCorrects
D1Classification / Membership / CapabilityGrant independent. One grant object, typed scopes; authority = a ResourceScope grant (terminology, not a 2nd object). Authority ≠ interest.participant type implied capability
D2Network is a first-class governed object, distinct from Tenant. One identity → many networks."network = a tenant with network.admin"
D3Generic event plane (ADR-0120). Transformation is a participant that subscribes+publishes, not a core primitive.no event/resource/authority plane
D4RequirementExpression — generic typed-predicate tree, three-valued (SATISFIED/UNSATISFIED/UNKNOWN). Absence of evidence ≠ satisfies not.flat required_credentials[]
D5Offering first-class (discovery) vs Service (executable).no single discoverable offering
D6WalletProvider interface; current store = default provider.wallet = the platform store
D7Operator neutrality explicit, audited, progressively removable; no silent self-grant.neutrality only at API layer
D8Generic async transaction state machine (idempotency / retry / timeout / dead-letter / compensation).synchronous-only federation
D9Unify durability + an immutable audit stream across planes.second KV store; no unified audit
D10Credential format is a codec — native signed-JSON now, W3C VC 2.0 later. No W3C assumptions in the kernel.format hardwired
D11IdentitySource + AssurancePolicy as governed Trust-plane objects.no IdP registry (single trust map)

Strengthened acceptance invariant. Adding a new domain may need new schemas, services, transformations and config — but must not need core-runtime edits nor new core objects merely for a new noun. A new interaction pattern requires an explicit platform ADR. Final proof: Avsar + TOP + public-health surveillance configured with an empty core-runtime diff and zero new core objects.

05The evolution plan

Evolve, don't restart. Trust-model-first; every phase has its own design-review gate before code. The async state machine lands before the Router so event delivery is never built synchronously then replaced.
