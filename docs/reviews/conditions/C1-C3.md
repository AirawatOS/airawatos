## Condition 1: B131. Verdict: HOLDS

### What I read
`verify/db_grant_audit.py` works out privileges for each of the three runtime roles on every `public` table and sequence. It uses `has_table_privilege` / `has_any_column_privilege` / `has_sequence_privilege`, which resolve membership, inheritance and PUBLIC. It also:
- forbids any `pg_auth_members` row for a runtime role or `migrator`;
- requires the login roles to be exactly the declared set;
- checks role attributes, SECURITY DEFINER functions, CREATE on `public`, and table owners.

This is the mechanism condition §5.1 asks for.

### Method
I used the harness `tmp/cond/c1.py`. For each mutation it did the following:
1. Applied the mutation through `psql` as the superuser.
2. Where it applies, proved the escalation is real: inside `BEGIN … ROLLBACK`, with `SET ROLE kernel_app`, a `DELETE … WHERE false` (or similar) was run. "runtime role CAN" means Postgres accepted the statement.
3. Ran `python3 verify/db_grant_audit.py`.
4. Reverted the mutation.
5. Ran the audit again.

Every revert succeeded and the audit passed after every revert.

### Why the condition holds
The original case (row 1) is caught on two independent grounds. Every variant that confers a privilege on the audit table itself is caught, by whatever route it is granted: group, nested group, NOINHERIT/SET, predefined role, PUBLIC, column, TRIGGER/REFERENCES/TRUNCATE, ownership, sequence (the slice's own self-test), and an undeclared login. That is the effective-privilege audit for every role, sequences included, that §5.1 requires.

### New findings

**C1-N1. Medium. Layer 1 (assurance net). Deadline: before Layer 2 exit.**

The audit enumerates only `pg_tables` (`relkind = 'r'`) in schema `public`. It never inspects rewrite rules or views. Postgres runs a view (default `security_invoker = false`) and a rule with their owner's rights. So an object owned by `migrator` hands the owner's DELETE/UPDATE on the audit tables to any role allowed to use that object.

Rows 8, 9 and 10 show `kernel_app` able to delete and update audit rows while the case "audit table … is append-only for every runtime role, by effect" stays ✓ and the audit exits 0. Row 11 shows the audit trail silently emptied by an INSTEAD rule, also green.

This is the same "owner-rights delegation" class the slice already closes for SECURITY DEFINER functions (check 5), so the module's claim "Anything not on the list fails, however it was granted" is not yet true.

I rate it Medium rather than High (unlike F5-1) for two reasons:
- The condition's mechanism is in place and correct.
- The residual needs a deliberate DDL object (a view or rule) that appears in the migration diff, not a bare GRANT.

Of the ratings in this report, this one is the closest call.

Proposed fix:
- Enumerate every relation `relkind in ('r','p','v','m','f')` in all non-system schemas, and apply the allow-list to all of them. A runtime role should hold no privilege on any view unless that view is allow-listed.
- Fail on any non-internal `pg_rewrite` rule whose target or action references an audit table, and on any rule on a runtime-writable table.
- Fail on any non-internal trigger on the audit tables.
- Add rows 8 to 11 to `db_grant_audit_selftest.py`.

**C1-N2. Low. Layer 1. Deadline: before Layer 2 exit.**

Grant options are not checked (row 2). `kernel_app` can re-grant its SELECT/INSERT on the audit tables to other roles at run time. The next audit would catch the result on a runtime role, but not a grant to a NOLOGIN role that nobody uses yet. Check `has_table_privilege(r, t, 'SELECT WITH GRANT OPTION')` and the equivalents.

**C1-N3. Low. Layer 1. Deadline: before first production.**

Two privileges are not checked:
- **Database-level CREATE (row 16).** It lets a runtime role create schemas and objects, a foothold for later object-based tricks.
- **`pg_default_acl` (row 4).** The audit only sees a future grant once a table exists, which is acceptable, but an empty `pg_default_acl` is a cheap invariant to assert.

**C1-N4. Info.** RLS policies grant no privilege, and BYPASSRLS is already checked (rows 6 and 7). No action.

## Condition 3: B117/B118. Verdict: HOLDS

### What I read
In `--strict`, `conformance/build_matrix.py` does the following:
- compares each file's whole `git` dict with `evidence.git_heads()` of the live five repos (exact dict equality);
- fails when the live tree is `+dirty`;
- checks every net against `verify/evidence-baseline.json`. The case count may not drop for any normalised name, the PASS count may not drop for any normalised name, the SKIP_BUILD total must stay within the ceiling, and an unknown mode has no baseline, so it fails.

### Method
I worked only on scratch copies and never touched `conformance/results`, `verify/evidence-baseline.json` or `docs/specs/STATUS-MATRIX.*`. The steps:
1. Cloned the five repos at their current HEADs into a scratch workspace.
2. Copied the real evidence files, re-stamped them to that HEAD and to a scratch `AOS_RUN_ID`, and copied the **real** baseline.
3. Ran `build_matrix.py --strict` with `AOS_RESULTS_DIR`, `AOS_EVIDENCE_BASELINE`, `AOS_MATRIX_OUT_MD/JSON` and `AOS_RUN_ID` pointing at the scratch copies.

The harnesses are `tmp/cond/c3.py` and `c3b.py`. The scratch workspace allowed dirty-tree tests without touching the live repos.

### Why the condition holds
Both original cases fail. Every head-equality neighbour fails: a mismatch on one of five repos, a short SHA, an extra key, a dirty tracked nested repo. The baseline neighbours that remove or demote a case also fail: a rename, PASS to XFAIL, a removed required file, an unknown mode, a SKIP_BUILD swap. That is the HEAD equality, the no-dirty rule and the per-net case baseline with SKIP_BUILD ceilings that §5.3 requires.

### New findings

**C3-N1. Low. Layer 1 (evidence). Deadline: before Layer 2 exit.**

The baseline is keyed by **normalised** name and tracks only counts. A case can be substituted while the counts stay the same:
- a renamed generated id (row 12);
- swapping between identical names (row 11, which already happens in the real vaultscope evidence);
- padding with a duplicate PASS (row 10).

In row 12 a distinct case disappeared with strict green. In the current real evidence no two *distinct* raw names collide; only identical raw names share a key. The exposure is therefore latent.

Proposed fix: also baseline the number of **distinct raw names** per key, or require a case to carry a stable `id` independent of its display name. Reject duplicate raw names within a net unless the case declares itself as a per-instance case.

**C3-N2. Low. Layer 1 (evidence). Deadline: before first production.**

`evidence.git_heads()` uses `git status --porcelain --untracked-files=no`. An **untracked** file in any of the five repos (row 7), and any gitignored file, therefore never marks the tree dirty. Evidence produced with uncommitted, untracked code can pass strict. `images_test.py` mitigates this for the reference image's `/app`, which is checked against the git tree by content.

Proposed fix: include untracked files that are not ignored in the dirty check, or record a hash of the build-context file list in the evidence.

**C3-N3. Info.**

Additions are not constrained (rows 16 to 18). New PASS cases, a second file for an existing mode, and an `env` relabel all stay green. With those, a forger can turn NO TEST into HELD or add a measured column. This is forgery, which is outside the stale/partial-evidence model behind B117/B118, so I record it without a deadline.

`--optional <net>` (row 19) silently waives a required net. This was already recorded among the earlier lower findings (F2-x, "`--optional` used silently"); the Makefile passes `--optional functional` in one target.
