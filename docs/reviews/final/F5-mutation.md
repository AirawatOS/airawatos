## Findings (checks that stayed green)

All are owned by Layer 1 (L1, the assurance nets and the installer/ops tooling they guard).

| id | check | severity | L1-owned Medium+? | finding |
|---|---|---|---|---|
| F5-1 | dbgrants | **High** | yes | Least privilege and append-only audit are judged on direct grants only. A NOLOGIN group role granted to `kernel_app` gives it UPDATE/DELETE on `kernel_admin_audit` and `kernel_authz_decision` (proven: has_table_privilege = t) while every case reads ✓. Fix: evaluate `has_table_privilege(role, table, priv)` for every login role × table × privilege (effective rights), and treat any role membership (`pg_auth_members`) of a service role as a finding unless declared. |
| F5-2 | vaultscope | **Medium** | yes | Tight services are probed only on `secret/` platform credentials and transit keys. A policy line granting a non-broker (decision) read on `components/data/*` (every tenant's component secrets) passes. So do grants on `auth/approle/role/*/secret-id` (impersonate another service) and `sys/*`. Fix: compare each live policy to its `.hcl` (exact), and/or probe capabilities on `components/*`, `auth/*`, `sys/*` for every service. |
| F5-3 | images | **Medium** | yes | The "every pip install is pinned" rule (R7-3) only parses segments containing the substring `pip install`. `pip3 install requests` (unpinned) passes. Fix: match `pip3?`, `python3? -m pip`, `uv pip` and similar, or fail on any `install` in a RUN not using the lock. |
| F5-4 | restore-drill | **Medium** | yes | The drill never destroys the host-side secrets it claims the backup covers (`.env`, AppRole env files), so `restore.sh` without the host-secret restore still passes. A real disaster restore (new host) is unproven. Fix: move `.env` and `vault/approle/` aside during DESTROY (and restore them only through restore.sh). |
| F5-5 | installer | **Medium** | yes | "no write helper swallows a non-2xx" is one regex for one spelling (`as e: return e`), and the live fault injection only raises synthetic failures at phase banners. A real write failure swallowed inside a phase (`as err: return err.code` in Phase 8) passes both, so the install can report "install complete" with a governance write missing. Fix: fault-inject at the HTTP layer (a failing write inside each Python phase helper) and assert the phase fails. Or require every helper to go through one shared, tested `_req` that records failures. |
| F5-6 | banned | Low | no | Hardcoded secret defaults evade when spelled as a named constant (`_DEV_DB_PASSWORD = "…"` / `DB_PASSWORD = "…"`): `PASSWORD_KWARG` needs a word boundary, and the env-default patterns need the literal inline. |
| F5-7 | routes | Low | no | FastAPI routes come only from `@app.<verb>` / `@router.<verb>` decorators in two files. `add_api_route` / `add_route` / a new router module is invisible to TEST 1 and TEST 2 (and to banned UNDECLARED_ROUTE). The docstring claims live `app.routes` introspection, which the code does not do. |
| F5-8 | decide-unit | Low | no | The unit tests cover only the `grant` kind. The two-key consent rule, `role:` rules and the unknown-kind fail-closed branch can be broken without a failure. Unwired today (RULES has only grant rules), so Low, but it becomes Medium the moment a consent or role rule is added. |
| F5-9 | fresh-install | Low | no | The "proven-empty slate" and "every volume created by this run" proofs cover only project-labelled / `airawatos-localdev_*` volumes. An external (or renamed) volume carries stale state through a "passed" fresh install. Fix: check the volumes actually mounted by every project container. |
