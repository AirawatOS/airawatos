# Re-check: Condition 4 (restore never destroys or modifies the live/previous set)

Independent reviewer, conditions-only re-check, 2026-11-10, about 02:20 to 02:40 UTC. Workspace HEAD 494cf9e (branch docs/trusted-network-platform-adr-0119-0120).
Scope: deploy/local-dev/restore.sh, _sets.py, backup.sh, _restore_check.py (slice-1k volume-set design). No tracked file was changed.

## Verdict: HOLDS for restore.sh as designed; two new Medium findings sit next to it

For every restore.sh failure, signal and parallel-start case I ran, the previous set stayed BYTE-IDENTICAL. That covers all 7 volumes (each file's name, mode, owner, size, mtime and sha256) and the sets/<set>/ files. The system could be recovered every time. The original live set L (`airawatos-localdev-r20261110T021033Z-4e5a1d`) still matched its very first fingerprint at the end of the session.

The F-C4-3, F-C4-4 and F-C4-5 failure modes are gone in the new design. The tiny-tmpfs `-prev-` volume is no longer used, a signal mid-switch now rolls back with a message, and a later restore never deletes earlier state.

Two neighbouring tools CAN destroy the live or previous set:
- **F-C4-6:** `restore.sh --recover` trusts the journal (it has no name or identity checks).
- **F-C4-7:** `_sets.py prune` takes the set name without normalising it, so its "refused for the active set" guard can be bypassed.

There is also a Low finding:
- **F-C4-8:** there is no lock between concurrent restores. A stale PREV makes the rollback start an OLDER set instead of the set that was actually live.

None of these is hit by a plain `restore.sh <backup>` run on its own. For that reason I rate the condition, read literally ("restore never destroys or modifies"), as HOLDS. F-C4-6 and F-C4-7 should be fixed before Layer 2 exit, because both are one step away from an operator mistake.

## Method

- **Backup:** a scratch backup of L was taken with `backup.sh /tmp/c4bk/good` (outside the repo, deleted at the end).
- **Stack stopped before each fingerprint:** I stopped the stack (`compose stop`) before every fingerprint, so PREV_RUNNING=0 and nothing restarts the previous set.
- **Fingerprint:** one container mounted all 7 `<set>_<vol>` volumes read-only and listed every entry with `stat` (name, mode, uid:gid, size, mtime, type) plus `sha256sum` of every file, about 4000 lines. Host side: `stat` and `shasum` of every file under sets/<set>/, plus the pointer. The tool was checked to be stable: two runs in a row gave the same hash.
- **Test sets:** to protect the shared live set, I first restored into sacrificial sets (R2 `...022330Z-7d31c6`, later R3 `...022804Z-4d47d2`, R4 `...023137Z-27d59f`). These became the PREVIOUS set for the destructive cases. L was fingerprinted every time as well.
- **Timing:** a full restore takes about 20-25 s (RTO 19-21 s).

Not run, assessed by reading instead:
- **Docker daemon killed mid-cut-over.** `remove_new_set` ignores `volume rm` errors and then deletes the journal, which leaves orphan new-set volumes. PREV is never touched.
- **Pointer replaced by a regular dir or file.** `active()` returns "", so PREV is empty. `switch` cannot replace a directory and fails, which triggers a rollback. A regular file is replaced, and the rollback `rm -f`s it. No set data is touched.
- **Host secrets of the previous set as symlinks.** restore.sh never opens the previous set's dir, and `prune` uses `rmtree`, which does not follow symlinks inside the tree.
- **Pre-created volume with the new set's exact name.** The name has 24 random bits and is checked before creation. Note that `docker volume create` silently reuses an existing name, so there is a tiny race between the check and the create. Info.

## NEW findings

### F-C4-6 (Medium; L1 deploy/local-dev `restore.sh --recover`): recover trusts the journal and can delete the active or previous set
- **Evidence:** cases 12-14. The only check is `case "$S" in "$P"-r*`. It does not check:
  - NEW != PREV;
  - NEW != the current pointer;
  - NEW matches the generated grammar `^<P>-r[0-9]{8}T[0-9]{6}Z-[0-9a-f]{6}$` (no `/`, no `..`);
  - that PREV exists.

  If `switch "$PREV"` fails inside the rollback, the code goes on under `set +e`. It then runs `up -d` on the NEW set and deletes that set's host secrets under the running stack. In every case it prints "previous set untouched", which is false.
- **Trigger:** a hand-edited, corrupted or stale journal. The journal lives in a 0700 directory, so this is an operator error or a local-tamper vector, not a remote one. The two paths are the destructive ones, sitting next to restore.sh, that the condition is meant to rule out.
- **Fix:**
  - Validate NEW and PREV against the strict grammar.
  - Refuse if NEW equals PREV or the current pointer while CUT=0.
  - Check that NEW's volumes carry the restore's own label or marker before removing them (for example, a `aos.restore.new=1` label set at `volume create`).
  - Make a failed `switch` inside the rollback abort loudly instead of continuing.
- **Deadline:** before Layer 2 exit.

### F-C4-7 (Medium; L1 deploy/local-dev `_sets.py prune`): the active-set guard is bypassed by non-canonical names; `prune ""` wipes every set's secrets
- **Evidence:** case 15. `prune` compares the raw argument with `readlink(active)` and then calls `shutil.rmtree(os.path.join(SETS, s))`.
  - `./<active>` and `x/../<active>` delete the live set's host secrets (POSTGRES_PASSWORD and every AppRole secret-id). Those can only be recovered from a backup.
  - An empty argument (for example `prune "$OLD"` with OLD unset) deletes `sets/` entirely.
  - `..` deletes `deploy/local-dev`.

  The volumes survive, because `set_volumes` uses an exact prefix match.
- **Fix:** accept only a name that matches the set grammar or is one of the names listed by `all_sets()`. Compare `realpath`s, and refuse an empty name, `.`, `..` and anything containing `/`.
- **Deadline:** before Layer 2 exit.

### F-C4-8 (Low; L1 deploy/local-dev `restore.sh`): no mutual exclusion between restores; a stale PREV restarts an older set
- **Evidence:** cases 9 and 10. The journal check happens before validation and the journal is written later, so two restores can both pass the check. Then:
  - A's success `rm -f`s B's journal.
  - B's rollback returns to the PREV it read at its own start (R3), not to SA, the set that was live at B's cut-over.
  - B restarts R3's stack (PREV_RUNNING=1 because SA's stack was running), which modifies the older set R3. The real previous set SA is left stopped and inactive.

  No data is deleted. The operator believes A's restore is live, but the system silently runs an older dataset.
- **Fix:**
  - Take an exclusive lock (`mkdir` or flock on `sets/.restore-lock`) for the whole run, and create the journal with `O_EXCL` at the first check.
  - Read PREV at cut-over time under the lock.
- **Deadline:** before Layer 2 exit (local-dev only). The production restore runbook needs the same exclusion before first production.

### Info
- **I-1:** `write_env` strips only lines that start with exactly `AOS_VOLSET=`. Other spellings (`export AOS_VOLSET=`, indented) stay in the new set's .env. They are harmless to compose, because the last value wins (verified), but anything that `source`s the file sees conflicting values. Suggest dropping every line whose key is AOS_VOLSET.
- **I-2:** an abort message names the last hook stage, not the real step. For example, a SIGTERM during `compose down` reports "stage 'secrets'", and a SIGTERM during `up -d` reports "stage 'switched'".
- **I-3:** leaks.
  - Every down/up cycle leaves the Vault container's 2 anonymous volumes behind; about 160 unnamed hash volumes exist on this host.
  - 14 `aos-restore-lists-*` temp dirs from earlier runs remain in $TMPDIR (none from this session). They are not secrets, but nothing removes them.
  - Owner: L1 deploy/local-dev, before Layer 2 exit.
