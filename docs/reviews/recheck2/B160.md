### (a) MET
- `deploy/local-dev/vault/entrypoint.sh:33-51`: the root is only *read* from init.json. The first-boot setup runs only when one is present. Otherwise it logs "no root token at rest" (`:50`). There is no generate-root call anywhere in the entrypoint. The healthcheck is `vault status` with no token (`docker-compose.dev.yml:78`).
- Boot paths:
  - First boot: `vault operator init` (`:23`) inherently creates the install root. That root is at rest in init.json, which is DEBT-B153 territory, not a regeneration.
  - Restart: reuses whatever is in init.json and generates nothing.
  - Restored volume: init.json is blank (backup.sh `:45-50`), so no root.
  - Installer re-runs: install.sh `:234-243` only reads, and aborts if the token is blank. It never writes init.json.
- The only writer of a generated root is `vault_root.py` (`ensure` `:65-71`, `write_root` `:40-45`).
- Drill callers:
  - `restore_drill.py:82`: `generate` at the START. In a `make verify` run this reuses the install root ("already present"). That token is not revoked before the backup. It rides into the backup's Vault storage (init.json is blanked, but the token-store entry is not). It is revoked only after the restore, by `revoke-all` (`:153-156`; evidence "revoked 2" = the restored pre-backup root plus the on-demand one).
  - `:141` generate → `:153` revoke-all → `:157` verify-none. Every generate in the drill is followed by revoke-all.
  - `verify_none` revokes its probe in a `finally` (`vault_root.py:102-107`).
- Not airtight on abnormal exit (F3). Other verify tests still read the install root from init.json and never revoke (vault_scope_test.py:58-62, ops_test.py:44-46, vault_renewal_test.py:46, net_doors_test.py:34, conformance_matrix.sh:12, run-both.sh:28). They depend on the first-boot root at rest (B153 scope). In `make verify` they run before the drill (Makefile:16), and the drill ends with no root.

### (b) MET
- Ordering in `restore_drill.py`:
  - restore at `:117-122`;
  - the "no root at rest" check (`:125-126`, `vault_root.py status` == absent) comes before the probes;
  - TIGHT probes `:129-133`, BROKER caps `:134-137`, health `:138-139`;
  - only then the first post-restore generate (`:141`).
- Coverage: all 12 Vault-using compose services. TIGHT covers kernel, network, identity, scheduler, automation, event-relay, app-host, decision, workflow and runtime-manager (`vault_scope_test.py:20-34`). BROKERS covers secrets and model-gateway (`:40`). This matches the 12 services with approle env_files in docker-compose.dev.yml.
- Root is excluded:
  - The probe takes the token from the container's own process environ (`vault_scope_test.py:66-71`), set by the AppRole login in `deploy/runtime/airawat-entrypoint.sh:25-45` after the restore.
  - A root token would read the FOREIGN path (200), and the case requires 403.
  - Evidence: every TIGHT own path → 200, foreign → 403. Broker caps are create/read/update(/delete).
- Weak spots (Info):
  - OWN accepts 404 (`restore_drill.py:132`).
  - Brokers are checked by `capabilities-self`, not by an actual read.
  - The health check exempts any container whose name contains "nginx" (`:139`).
  - None of these weakens "own token, no root".
- See F5: a valid pre-backup root does exist in the restored token store during these probes. It is not generated, and the probes do not use it.

### (c) MET
- Fail on remaining root:
  - `restore_drill.py:157-158`: verify-none must exit 0.
  - `vault_root.py:101-124`: a fresh probe root lists `auth/token/accessors`, looks up every accessor, and fails on any root-policy token other than itself. It also requires init.json blank and the probe revoked.
- What the enumeration catches:
  - roots not recorded in init.json;
  - orphan service tokens (listed by accessor).
- What it cannot miss:
  - batch tokens cannot be root tokens;
  - Community Vault 2.2.1 has no namespaces.
- If revoke-all fails, its own case fails (`:155-156`: rc and n≥2), and verify-none fails independently. **Gap: F2.** Enumeration errors are fail-open.
- Break-glass procedure: `docs/operator/RESTORE-AND-ROTATION.md:197-219` covers:
  - KMS auto-unseal with recovery keys (`-recovery-shares=5 -recovery-threshold=3`);
  - a 3-of-5 quorum;
  - holders in at least two teams, with PGP-encrypted shares that are never kept on the host or in a backup;
  - a custody register (location, fields, accessor per use);
  - a ticketed procedure;
  - `revoke -self` plus an accessor lookup returning not found;
  - audit review and root enumeration;
  - a rekey on holder change.
- Rehearsal gate: `deploy/RELEASE-PLAN.md:196-205` makes the break-glass drill a GATE in Stage 1 rehearsal ("No go-live without a passed drill on record").

### B161: PARTIALLY MET
- In the drill: met (revoke-all by accessor enumeration, n=2, then verify-none 0).
- In an operator restore: not met (F1). `restore.sh` never calls `vault_root.py`, and the Restore steps in RESTORE-AND-ROTATION (`:72-97`) do not tell the operator to run `revoke-all` after a restore.

## Notes
- First boot still writes the install root to init.json (`entrypoint.sh:21-24`), and every `verify/*` and `conformance/*` net except the drill reads it from there. After a fresh install, local-dev therefore holds a root at rest until a drill or restore revokes it. This is outside the owner's condition (which concerns the regenerated root) and is covered by B153 for production. Recorded here so it is not mistaken for "no root at rest" generally.
