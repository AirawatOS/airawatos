ADR-0092 · Proposed · 2026-09-18

Unified Settings & the Component Configuration Model

One typed configuration contract per component, one rule for what is a secret, and one two-tier Settings home — collapsing today's Marketplace / Connections / Components / Setup / City-Setup sprawl.

design-onlygrounded in Airawat source absorbs ADR-0027 · ADR-0075

01The problem, precisely

"Configure this component" has four partial homes today, none complete — so a value a component declares can end up with no reachable UI. That is what happened to osm-transit's PBF.

02The model — field kind decides the store

Collapse today's three separate meta lists (secrets: / assets: / config:) into one typed contract. Each field's kind deterministically picks its store — and only secret is eligible for the Vault. "Secret" becomes a property of the field, checked at certify, not a convention.

03The surface — one Settings, two tiers

Promote Settings from the profile menu into a first-class home, split like iOS: personal settings for every user, component settings for admins. A single generic renderer draws every field kind from the contract, so every field has exactly one home.

04Consolidation — what each app becomes

TodayBecomes
MarketplaceUnchanged — discover + install only. Clean line: store vs. Settings.
ConnectionsA category inside Settings (external creds + endpoints). Its generic renderer becomes the renderer.
ComponentsConfig moves into Settings; the reads/writes/egress/logs view stays as a component detail panel.
Setup (ADR-0075)Settings' guided-flow engine. Its asset step configures inline instead of pointing elsewhere.
City SetupStays a domain wizard (AOI + OSM + GEE) but writes through the contract; its private bind loop → shared auto-bind.
Org Setup · AdminUnchanged (governed org data / users↔roles); linked from Settings for discoverability.

+ Install auto-binds assets

  • Install reuses an existing same-kind asset (e.g. the tenant's one OSM PBF) for every driver that declares populates.
  • Kills the "installed after City Setup → orphaned" bug class — the exact osm-transit failure.
  • Manual override stays in Settings.

Migration slices (later, for approval)

  • 1 · platform.component_config + certify-time secret validator
  • 2 · unified contract loader (shims old meta)
  • 3 · generic renderer + Settings shell (2 tiers)
  • 4 · install auto-bind
  • 5 · re-home Connections/Components/Setup; City Setup writes through the contract

05Solutions — set a shared field once, fan it out

A solution installs many components (City Setup provisions the ~19-member City Baseline). You must not configure members one by one. Shared fields — AOI, OSM PBF, GEE key — are set once at solution scope and fan out to every member that declares a matching field kind, including members added later.

06Observability — configure, observe, get told

A model that can schedule components must give a durable way to watch them. Today run history is effectively in-memory (a scheduler restart read a run's history back as zero), there's no cross-component "what's running now", and no completion signal. Settings configures; a first-class Activity surface observes; the Inbox tells you when something needs you.

Immediate, separate from the redesign

osm-transit's PBF can be bound today in the existing Connections app (its generic uploader lists any component declaring assets[]) or by re-running City Setup's OSM step — not Marketplace/Components, and no secret hack needed.
